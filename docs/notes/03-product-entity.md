# 03 - Product entity, JPA mapping, and optimistic locking

## The problem this entity solves
Two customers buy the last unit of the same product at nearly the same instant. Both read
`stockQuantity = 1`, both decide to proceed, both decrement it. Without protection, stock goes
to -1: an oversell. `@Version` turns this from a silent bug into a loud, catchable exception.

## Field-by-field decisions

| Field | Type | Why |
|---|---|---|
| `id` | `Long`, `@GeneratedValue(IDENTITY)` | Database assigns primary keys (auto-increment) |
| `name` | `String`, `nullable = false` | A nameless product is a data bug |
| `sku` | `String`, `unique = true` | Human-facing product code, must never collide |
| `priceCents` | `long` | Whole cents, not `double` — see below |
| `stockQuantity` | `int` | Mutated only via `decreaseStock()`, never a public setter |
| `version` | `Long`, `@Version` | Hibernate's optimistic-locking counter |

Hibernate generated this DDL straight from the annotations:
```sql
create table products (
  stock_quantity integer not null,
    id bigint generated by default as identity,
      price_cents bigint not null,
        version bigint not null,
          name varchar(255) not null,
            sku varchar(255) not null unique,
              primary key (id)
              )
              ```

              ## Design choices worth defending in an interview
              - No-arg constructor is `protected`, not `public`. Hibernate needs one via reflection, but a public
                one would let any code build a half-initialized `Product` with null fields.
                - No `setStockQuantity()`. Stock only changes through `decreaseStock()`, which refuses to go negative.
                  A public setter would let that invariant be bypassed entirely.
                  - `priceCents` is a `long`, not a `double` or `BigDecimal`.
                    - `double`/`float` store binary fractions (powers of two), so decimal values like 19.99 aren't
                        stored exactly — money math drifts after enough operations.
                          - `BigDecimal` is the textbook-correct alternative, but it's a heap object: `.equals()` compares
                              scale too (`2.00` != `2.0` by `.equals()`), so every comparison must use `.compareTo()`, an easy
                                  mistake to make. Some teams use it anyway; it's a real trade-off, not a hard rule.
                                    - Integer cents (`long`) sidesteps rounding entirely: plain integer arithmetic, no rounding modes,
                                        primitive equality. Stripe's own API represents amounts this way. Cost: convert to decimal only
                                            at the display boundary, and it assumes two-decimal currencies (a gap for later multi-currency work).
                                            - `spring.jpa.open-in-view=false`: keeps the DB connection scoped to the transaction, not the whole
                                              HTTP request. Forces all data access through explicit `@Transactional` service methods, and avoids
                                                hiding N+1 queries or lazy-load exceptions inside the view layer.

                                                ## How `@Version` actually works (compare-and-swap, not a value comparison)
                                                1. Two requests read the same row: `stock=1, version=0`.
                                                2. Request A saves first. Hibernate runs
                                                   `UPDATE products SET stock_quantity=0, version=1 WHERE id=? AND version=0`.
                                                      The `WHERE version=0` matches, so it succeeds. Row is now `version=1`.
                                                      3. Request B still thinks version is 0, so its `UPDATE ... WHERE id=? AND version=0` matches
                                                         **zero rows** (the real row is already at version 1).
                                                         4. Hibernate checks the affected-row count. Zero, when one was expected, is what throws
                                                            `OptimisticLockException`. There's no separate value-comparison step — the mismatch is detected
                                                               by the update silently matching nothing.

                                                               This is *optimistic* locking: assume conflicts are rare, check only at write time. The alternative,
                                                               *pessimistic* locking (`SELECT ... FOR UPDATE`), blocks the second reader up front instead.
                                                               Trade-off: optimistic locking needs retry logic in the service layer (next phase);
                                                               pessimistic locking trades that away for reduced throughput under contention.

                                                               ## Interview one-liners
                                                               - "My Java entity is the schema description. Hibernate derives the DDL from the annotations."
                                                               - "I use optimistic locking via `@Version` so concurrent stock updates fail loudly with a retryable
                                                                 exception instead of silently overselling."
                                                                 - "I store money as integer cents to avoid binary floating-point rounding, with `BigDecimal` as the
                                                                   documented alternative if we needed exact-scale arithmetic beyond simple cent counts."
